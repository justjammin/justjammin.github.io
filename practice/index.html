C1 / Core competencies

Agentic Engineering

ADVANCED TECHNIQUE

Optimistic concurrency control for parallel coding agents.

Agents work independently, but their changes must still pass a controlled integration step.

S

Situation

Multiple agent tasks can overlap in files or depend on code that changes while they work.

T

Task

I would increase useful parallel execution while preventing stale work and conflicting edits from reaching the integration branch.

A

Action / proposed

  1. I would give each task an isolated worktree, a base commit, permitted write paths, acceptance checks, and an explicit dependency list.
  2. I would schedule independent tasks concurrently and serialize work whose interfaces or write sets overlap.
  3. At integration, I would compare the task's base and changed files with the current branch. A stale dependency would trigger revalidation or rework rather than a blind merge.
  4. I would run checks on the combined branch and retain human approval for externally visible changes. A path allowlist would be paired with process isolation; it is not a security boundary by itself.
R

Result / expected

More parallel work could integrate successfully without increasing rework or escaped defects.

HOW TO VALIDATE

Measure accepted changes per engineering hour, conflict frequency, rework, and post-merge failures across comparable tasks.

TRADEOFF

Isolation and integration checks add overhead. Small, tightly coupled changes may finish faster as one task.

SAY IT OUT LOUD

“I would treat parallel agent output like concurrent transactions: isolate the work, detect conflicts, and validate the combined result before accepting it.”

C2 / Core competencies

Data contracts and migration design

ADVANCED TECHNIQUE

Transactional outbox with idempotent consumers.

The database records both the business change and the obligation to publish it.

S

Situation

A lead can be saved successfully while its downstream notification fails.

T

Task

I would close that failure gap during migration without claiming exactly-once transport.

A

Action / proposed

  1. I would write the lead and an outbox event in the same database transaction.
  2. A dispatcher would claim committed events, publish them with bounded retries, and mark confirmed delivery. A crash could cause a repeat, so each event would keep a stable ID.
  3. Where I control the consumer, I would record that ID and apply its database effects atomically. External side effects would need their own idempotency support or reconciliation.
  4. I would compare legacy and new outputs in shadow mode before moving traffic by tenant or cohort.
R

Result / expected

Committed leads would retain a durable publication obligation, and retries could recover delivery without repeating protected business effects.

HOW TO VALIDATE

Inject crashes before commit, after commit, and after publish but before acknowledgement. Reconcile persisted leads, outstanding events, and downstream effects.

TRADEOFF

Outbox retention, dispatcher operations, and eventual consistency add complexity. A durable dispatcher can initially use HTTP; a broker is optional.

TECHNICAL REFERENCESAWS transactional outbox ↗

E1 / Experience bullets

Python services and API scale

ADVANCED TECHNIQUE

Bulkheads, end-to-end deadlines, and retry budgets.

Isolate slow dependencies so one failure cannot occupy every worker.

S

Situation

Python and PHP services call dependencies that can become slow or intermittently unavailable.

T

Task

I would preserve useful throughput and bounded response times during partial failure.

A

Action / proposed

  1. I would allocate an overall request deadline and smaller connection and response budgets to downstream calls.
  2. I would reuse HTTP connections and bound concurrent calls per dependency, with limits coordinated across replicas and downstream capacity.
  3. I would retry only appropriate transient failures within a shared budget, adding backoff and jitter. Writes would require idempotency support or explicit reconciliation.
  4. I would expose saturation and rejected-work metrics and test cancellation to ensure timed-out requests release resources.
R

Result / expected

A slow OEM or service could degrade its own traffic without exhausting capacity needed by healthy integrations.

HOW TO VALIDATE

Inject slow responses, dropped connections, and overload. Inspect tail latency, pool occupancy, retry amplification, and successful completion under failure.

TRADEOFF

Bounds intentionally reject or defer some work. Queued handling is an option only where the business contract permits asynchronous completion.

E4 / Experience bullets

MySQL performance and Redis caching

ADVANCED TECHNIQUE

Query-plan optimization followed by stampede-resistant cache-aside.

First reduce the underlying work; then prevent repeated work safely.

S

Situation

Slow ORM-driven queries increase database load across multiple application pods.

T

Task

I would reduce expensive database work while defining where cached data may be stale.

A

Action / proposed

  1. I would group slow queries by shape, identify N+1 access, and inspect actual plans and row counts using a supported `EXPLAIN ANALYZE` on safe representative reads.
  2. I would test query rewrites and composite indexes against actual predicates, joins, and ordering, including their write and storage costs.
  3. For suitable read paths, I would add shared Redis cache entries with versioned keys, bounded lifetimes, and single-flight regeneration with lock expiry.
  4. I would define invalidation and version checks to prevent a stale read from repopulating invalidated data. I would bypass caching where freshness is essential.
R

Result / expected

Queries would perform less work, and hot-key bursts could avoid simultaneous database refills.

HOW TO VALIDATE

Compare query plans and latency under matched load; test cold cache, hot-key expiry, failed regeneration, and update/read races.

TRADEOFF

`EXPLAIN ANALYZE` executes the statement. Added indexes slow writes, and caching creates consistency obligations.

  3. Where the provider and application support overlap, I would retain the prior configuration until the new path is validated, then retire it deliberately.
  4. I would probe valid and invalid assessment flows and watch rejection rates and legitimate form completion without logging tokens or customer payloads.
R

Result / expected

Configuration mismatches could be detected before broad exposure, with an explicit recovery path if legitimate submissions fail.

HOW TO VALIDATE

Test wrong environment mappings, expired or reused tokens, unexpected actions, and both relevant form types using supported test mechanisms.

TRADEOFF

An old key may need immediate retirement after compromise. Recovery must not silently bypass verification or weaken the agreed abuse policy.
